# UniSeek beta：独立搜索、优先队列逐项展示

歌手在前端本地搜索；视频关键词、UP 主关键词和可选编号查询独立并发。结果先进入前端缓冲区，每 90 ms 最多释放一张卡片：虚拟歌手优先，其次 AV/UID 精确命中，再从歌曲和创作者中选择 `(已展示同类数量 + 1) / 权重` 最小的一类，歌曲权重为 3、创作者为 1，同值歌曲优先。两类都有待展示项时约按 3:1 交错，后到的歌曲能立即参与下一次选择；不比较跨类型后端 score。

歌曲首批尚未完成时最多先展示 2 位普通创作者，剩余创作者暂存；歌曲成功、为空或失败都会解除限制，不因失败永久卡住缓冲区。每类保留接口顺序，已展示卡片不重排；相同 type/id 在缓冲区和列表中统一去重，后到的资料或指标补充原位置。创作者成功后只请求一次，失败可单路重试。缓冲区排空后才允许继续请求歌曲下一页。

新卡片使用 270 ms、4 px 高斯模糊与淡入，只有刚入场的少数卡片参与动画，无逐帧 JavaScript 或常驻 will-change。结果区顶部的「结果入场动画」开关保存在本地，关闭时保持队列交错逻辑；系统 `prefers-reduced-motion` 自动禁用动画。切换关键词、视频范围或离开页面会取消请求、清理缓冲区与唯一的释放定时器。页面已删除「已加载多少条」，改为显示「按相关性排序」及可聚焦、点击的排序说明。

2026-11-04 更新：开发者已完成 ADM 搜索宽表及首批数据构建，歌曲关键词和 AV/BV 搜索统一改读 `hantang_dynamic.adm_uniseek_videos`，并已反馈应用使用新表的响应样本。在线不再关联原始视频或 Daily，不探测 Daily 最新日期；数据生成、授权与发布见 [ADM SQL 使用说明](../../../../sql/adm_uniseek_videos.md)。

## 视频范围

UniSeek 页面与首页共用导航栏的 `subtle` 淡化模式，首屏采用轻薄的透明底层与辅助文字色，滚动后加强填充及背景模糊；样式和主题参数与首页共享，不在搜索页另写导航配色。

2026-11-20：搜索区域默认收起选项，仅保留一行搜索框；搜索按钮右侧的箭头按钮展开/收起「全部视频」「虚拟歌手歌曲」「虚拟歌手中文曲」，默认第三项。折叠按钮和选项均提供英语及日语文案，隐藏时保留选择。URL及视频请求使用`contentScope=all|virtual_song|chinese_virtual_song`；前端缺省或未知URL值回到默认范围，后端对显式非法参数返回400。修改关键词保留所选范围，切换范围从第一页重新查询，旧请求和缓冲结果取消。

2026-11-25：搜索栏使用与控件同高的圆角亚克力底层，不留外围内边距和控件间隙。半透明背景及外阴影常驻，滚动继续增强背景模糊；展开后的范围选项独立位于搜索栏下方。主输入使用无边框 `Input` 和共享 `.ds-filter-control.ds-filter-control--transparent`，悬停、聚焦沿用日期范围控件的 Canvas / Secondary 填充。搜索和展开按钮均保持图标形式，统一使用透明底的 Normal，展开后也不改为 Secondary；悬停、按下、禁用和键盘焦点复用共享规范。透明底修饰类只在 `design-system.css` 维护，亚克力参数集中在 `theme.css`，不叠加描边、焦点阴影或覆盖按钮的输入层。

输入去除首尾空白后超过 3 个字符，且完整匹配正数字 aid、AV 前缀编号或完整 BV 编号时，Ant Design `AutoComplete` 显示「直达歌曲详情」候选。复用已有 BV → aid 解析，保留 64 位字符串精度；不完整、非法、前导零或超出正 64 位范围的编号不出现候选。点击候选或方向键选择后回车直接跳转 `/videos/:aid`，不先查搜索接口、不受当前搜索标签范围限制；输入本身不会自动跳转，也不宣称视频已收录。未选择候选时回车和搜索按钮仍执行原有搜索，数字歌名及 UID 搜索保留。

三个范围都以当前ADM候选为基础。全部视频不读取标签表，保留未打标及非歌曲；虚拟歌手歌曲使用标签表`is_virtual_singer_song`；中文范围使用`is_chinese_virtual_singer_song`。两个筛选范围通过aid的EXISTS在评分及1000条截断前筛选，包含混合演唱，多语中包含汉语即可进入中文范围。无标签、未知或明确不符合条件的投稿不进入这两个范围，不在结果为空时回退到全部视频。

关键词、AV/BV编号入口及后续分页使用同一范围；虚拟歌手资料、UP主关键词及UID结果保持独立，不用投稿语言或标签过滤账号。歌曲列表页尚未接入本次范围选择。

## 查询来源

- **虚拟歌手**：前端打包 [18 位歌手的轻量配置](../../constants/vocal/vocal-search-info.json)，同步匹配名称和别名的子串，忽略大小写；“初音”命中“初音未来”，“天依”命中“洛天依”。名称/别名完全匹配在本地同类结果中优先。不分页，不发后端请求。ID 和立绘与前端详情目录保持一致，不伪造相关投稿数。
- **歌曲关键词**：`GET /uniseek/videos?keyword=洛天依&page=1&pageSize=30&contentScope=chinese_virtual_song`。page 从 1 开始，pageSize 默认 30（1–50）。响应 result 包含 keyword、page、pageSize、list、hasMore、nextPage、videoLimit（1000）。仅在 hasMore=true 时继续请求 nextPage，翻页无需等待其他来源。
- **UP 主关键词**：`GET /uniseek/producers?keyword=天依`。仅检索 videos_filtered > 0 且 face 含非空白字符的账号，按名称匹配，最多返回 20 位，不分页。响应 result 为 keyword、list。不会联查视频或快照。
- **视频编号**：`GET /uniseek/videos/{aid}?contentScope=chinese_virtual_song`。纯正整数字符串额外尝试精确 AV；显式 av/AV 或 BV/bv 先在前端解析成 aid，仅查询精确视频而不再发歌曲关键词请求。ID 按字符串传输，保持 64 位精度。直接按 ADM 主键等值查询并应用同一标签范围，不另查原表或旧日快照。
- **UP 主编号**：`GET /uniseek/producers/{userId}`。纯正整数字符串额外精确查 UID，且仍要求 videos_filtered > 0、face 含非空白字符。带 AV/BV 前缀的输入不当成 UID。

编号接口统一响应 result.list，无匹配或未进入已发布搜索集时成功返回空数组。未收录不代表视频在原始库中不存在；站内详情资料接口仍用于页面资料展示。

普通文本同时启动两个关键词请求；纯数字同时启动两个关键词请求和两个编号请求。数字文本搜索仍然保留，不做 aid/user_id 转字符串的 LIKE。`123abc`、超出正 64 位范围或带前导零的数字文本不发编号查询。“天依”先显示本地歌手，后面的歌曲与 UP 主按缓冲区优先级逐项出现。编号精确命中在尚未展示的结果中优先，不移动已展示的卡片。

搜索接口均使用项目 `ResponseDTO` 信封。无匹配是正常成功结果 `list: []`。服务端失败保留为独立、可重试的错误。切换关键词或离开页面会取消 fetch，并阻止旧响应写入新结果。某一路失败不清空已加载结果，重试只重新调用失败来源。下一页失败保留列表和 nextPage，可单独重试。

## 数据与同类排序

页面以紫色虚拟歌手 Tag、橙色创作者 Tag、绿色歌曲 Tag 区分实体类型，均适配日夜主题。虚拟歌手的内部 ID 只用于链接与去重，不在卡片上展示。

歌曲结果同时显示达到的最高播放荣誉，复用歌曲列表的 `VideoHonor`：殿堂蓝、传说橙、神话紫，统一为带奖杯图标的无边框 Tag / Chip，与绿色歌曲标签并排。直接使用 `payload.play` 判定，缺失或未达 10 万时不显示，不回退显式 NULL，也不追加逐项快照请求。

每项为 type、id、title、subTitle、coverUrl、jumpUrl、payload，不对外提供可跨类型比较的 score。所有列表实体 ID 为字符串。

视频封面来自 ADM 的 pic，头像来自 discovered_users.face，立绘复用 frontend/public/vocals。歌曲关键词与编号查询的 payload 包含 bvid、play、favorite、like、coin、publishDate（Unix 秒）、producerId、recordDate。recordDate 为已发布批次的来源日 D，不要求是今天，也不使用每个视频各自的最新日期。ADM 离线发布时已过滤 `processed_videos.is_deleted = false`、D 日有 Daily 记录且累计收藏数严格 **> 100** 的视频；100、0、NULL 均不入表。其他指标缺失时保留 null，真实 0 保留 0。

旧点赞版的数据库约束及刷新过程需按[迁移操作步骤](../../../../sql/adm_uniseek_videos_favorite_migration.md)升级并重新发布。点赞不参与新门槛，原始 0 / NULL 保留，不由此次改动补齐。

UP 主关键词 payload 包含 uid、fanCount、videoCount（videos_filtered，上游过滤投稿数）、totalView（filtered_view）；编号查询使用相同的收录投稿数与头像条件。

视频和 UP 主各自在 SQL 中排序，服务端不合并两类数据或做跨类型比较：

- **暂行歌曲评分，总分为匹配源、标题匹配度与播放量分相加**。前两项各满分 100；播放量权重按查询词选择，普通查询为 100，热度优先查询为 500。未来仍需建立虚拟歌手、歌曲与创作者的统一模型，不把此公式视为最终方案。
- 匹配源分：标题完全一致 100，包含完整关键词 70，其他匹配 40；关键词恰好等于目录中的虚拟歌手名称或别名时，仅此项除以 10（忽略大小写和首尾空白，子串不触发）。Maven 从前端 `vocal-search-info.json` 打包后端资源，双方共用一份目录。
- 标题匹配度：`min(100, 100 × 关键词长度 / 标题长度)`，按给定的长度比例对所有命中计算，包括仅数组命中；空标题为 0，短标题封顶 100。
- 播放量分：`viewWeight × min(1, ln(1 + max(播放量, 0) / c) / ln(10000001 / c))`，保留 `c = 100` 和原有归一化公式。NULL 仅在评分时按 0 处理，一千万播放达到神话曲门槛并封顶，超出不再加分。
- 热度优先只在**整个关键词**精确等于歌手名称、已有别名或补充词名单中的词时触发（忽略大小写及首尾空白）。歌手复用 `vocal-search-info.json`；CP / 主题词在后端 [`uniseek-ranking.json`](../../../../src/main/resources/config/uniseek-ranking.json) 的 `popularityKeywords` 中维护，当前只有「南北组」，不自动把所有 Tag 当作热度词。该文件同时维护 `defaultViewWeight = 100` 和 `popularityViewWeight = 500`，可统一改成 800；修改后需重新构建、重启后端。
- 「洛天依」「乐正绫」「南北组」使用 500；「霜雪千年」「洛天依 霜雪千年」「南北组 原创」仍使用 100，避免歌名或带限定条件的查询仅因包含歌手／CP 名就被热度主导。歌手原有匹配源分除以 10 的规则保留，CP / 主题词不额外降低匹配源分。三个内容范围共用此规则，精确 AV/BV 查询不参与评分。
- 按空白拆分词，每个词都必须在标题或某个精确 tag_new/participle/label_singers 元素中命中，不搜索 description 或旧 tag 原文。
- 一、二字符短词也参与标题子串匹配，不再受原大表路径的短词限制。标签/分词/歌手数组仍为完整元素匹配；输入中的 `%`、`_`、反斜杠按字面搜索，参数化查询不拼接用户输入。
- 在 ADM 所有匹配项上计算上述三项总分，再按 `score DESC, aid DESC` 截取最多 1,000 首。先完成收录和全体匹配项评分，再限制返回数量，避免先截断导致高分结果丢失。单个关键词的 1,000 首上限仍是 beta 契约。
- UP 主先在 WHERE 过滤 videos_filtered > 0（0/NULL 不参与）且 face 含非空白字符（NULL、空字符串、纯空白均不参与），再按名称与去除首尾空白的关键词逐字完全一致优先（大小写也需一致）、fans 降序 NULLS LAST、user_id 降序排序，最后 LIMIT 20。名称候选仍由 ILIKE 不区分大小写匹配。完全命中不会因粉丝少被候选截断。

## 发布批次、缓存与分页

仅「全部视频」按原关键词和ADM发布批次 UUID 缓存 **60 秒**，最多 **16 个键**、每个最多 1,000 条。该范围每页先从 ADM 读取一行 batch_id；发现新批次后不复用旧缓存，同日补算也能生效。缓存未命中时只运行一条 ADM 排序查询，并以该查询实际返回的批次存储缓存，避免两次查询之间发生发布而错误标记缓存。无匹配不缓存；空表返回空数组并清空结果缓存。

两个虚拟歌手范围暂不使用应用结果缓存，每页在一条SQL快照中重新筛选已提交标签、评分并切页。入库可能由不同进程完成，ADM批次未变时也应立即反映新标签；不依赖本进程通知、不新增发布版本表，也不在每次请求扫描全表求MAX(labeled_at)。每页仍有1000条返回上限和5秒查询超时，实际业务库性能需再观测。

全部视频翻页复用缓存中的原顺序；两个标签范围重新计算相同相关性公式，不重新搜索 UP 主或歌手。接口没有固定批次游标，跨发布、标签变更或缓存过期时仍可能发生跨页漂移，前端继续去重；正式快照分页留作后续。AV/BV 等值查询独立于关键词评分与结果缓存。

## 部署与验证

[ADM 建表与同步 SQL](../../../../sql/adm_uniseek_videos.md) 由开发者手动执行；用户已确认首批构建完成，截图客户端显示 72,992 行，该数字不作为日常发布规模保证。应用只要求搜索表及其发布字段可读，不查询发布控制表，不自动安装扩展或注册 CRON。新路径无需 pg_trgm 或原表的 [旧搜索索引脚本](../../../../sql/uniseek_search_indexes.sql)；使用 ADM 自身的 aid 主键、bvid 唯一索引和三组数组 GIN。标题 ILIKE 可能扫描小表，实际计划取决于词和数据。

其他环境部署时需要重新构建、重启后端，并确认应用实际账号的 schema USAGE、搜索表及[标签表SELECT权限](../../../../sql/video_content_labels_permissions.sql)；建表账号有权限不代表应用账号也有。查询在只读事务中禁用本次 JIT，每条查询超时 5 秒；工作线程最多 4 个，队列 32 个，队列满返回 503。参数错误返回 400，数据库失败（包括缺表、权限不足）返回 500，不伪造为空列表、不隐式回源。刷新失败由离线事务保留上一成功批次。

前端测试验证晚到歌曲插队、3:1 交错、创作者首批限制、歌曲失败后解除限制、逐项释放、两字歌手名、数字与 AV/BV 分流、去重与补充字段、单路重试、缓冲期间分页背压以及切换关键词后的请求与定时器取消。后端 HTTP 测试阻塞歌曲查询，确认 UP 主响应仍能先完成。页面手动验收入口 `/uniseek?keyword=天依`、`/uniseek?keyword=初音`、`/uniseek?keyword=123456`。

后端 DAO/Service/HTTP 回归覆盖 ADM 来源、同日批次失效、发布与读取交错、缓存容量/过期、64 位编号、分页、空表与独立错误，并验证三个范围的歌手／CP 权重选择与复合查询边界。SQL 回归直接提取生产 DAO 的查询，在只建 ADM、不建原始视频或 Daily 表的内存 PostgreSQL 上验证标题/数组匹配、热度优先与歌名相关性排序、一千万封顶、完整评分后截取、NULL/0 指标及 UP 主排序：

```sh
PGLITE_MODULE_PATH=/path/to/@electric-sql/pglite/dist/index.js node sql/tests/uniseek.test.mjs
```

开发者反馈新表搜索首次视频响应约 **700 ms**，第二次及后续下滑约 **100 ms/次**。旧聊天记录中的热门二字词、应用缓存未命中首查约 **3–4 秒**，粗略对比首次提速约 **4.3–5.7 倍**、耗时减少约 **77%–83%**；旧分页响应未单独记录。此前约 512 ms 是最新日期定位子步骤，不是整次搜索响应。

本次使用已有聊天数据，没有重新测试旧逻辑或连接业务库。关键词、负载、测量位置及数据库缓冲区状态未统一，不能当作 P50/P95 或纯 SQL 基准；后续持续测量新路径的热门词、短词、编号及并发分布。过程、职责和边界见 [技改复盘](../../../../doc/design/uniseek/adm-search-retrospective.md)，后续见 [Elasticsearch 与正式排序 TODO](../../../../doc/todo/uniseek-elasticsearch-ranking.md)。
