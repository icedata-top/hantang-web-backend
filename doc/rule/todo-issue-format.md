# TODO / Issue 编写约定

适用于 `doc/todo/` 下的待办文档及项目 issue。目标是让其他开发者和 AI Agent 能理解问题、当前状态和下一步，不要求每篇文档套用全部章节。

- 使用具体标题，说明要解决什么问题或完成什么结果。
- 正文至少清楚表达当前问题与期望结果，可以用短段落完成，不强制章节数量。
- 明确区分已知事实、已确认范围、候选方案及待确认问题；没有确认的内容不要写成已定需求。
- 状态应符合实际，例如待讨论、待实施、受阻或已完成；提出方案、编写 DDL 不等于实现或建表成功。
- 引用相关代码、SQL、设计和前置待办，使用可定位的相对链接；避免复制多份容易分歧的结构定义。

按实际需要选择以下段落，所有段落均为可选，不为凑模板添加空章节：

- **需求背景**：现状、触发原因、受影响的用户或功能。
- **目标与范围**：本次完成什么，哪些内容延期或不在本期。
- **技术方案**：已确认或候选实现方式、数据口径及涉及模块；标明方案状态。
- **卡点与待确认问题**：缺少的数据、未确定的规则、外部依赖及需要谁补充的信息。
- **实施步骤**：有实际价值的工作拆分和先后关系，不预设尚未确认的排期。
- **验收与验证**：如何判断结果可用，如何检查正确性和性能。
- **后续计划**：延期能力及与本期的边界。

简单问题可以只写几句话或检查清单；复杂问题再使用多个章节。不要把讨论草稿自动升级为最终 PRD。
