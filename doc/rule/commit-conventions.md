# Git commit 规范

适用于本仓库后续新增的提交，包括开发者和 AI Agent 创建的提交。已有提交不为统一格式而重写历史。

## 标题格式

```text
<type>(<scope>): <中文摘要>
```

类型与范围使用小写英文；使用英文半角冒号，后跟一个空格。冒号后的摘要使用中文，可以保留 API、UI、aid 等技术名词、组件名和路径。摘要直接说明最终改动，保持简短，不写「修改一下」「更新内容」等无法判断用途的描述。

```text
feat(video): 新增历史数据接口与累计增量趋势图
feat(navbar): 优化移动端顶栏与抽屉导航
fix(video): 修正缺失快照时的增量计算
doc(ui): 补充组件选型与主题配色规范
refactor(frontend): 复用日期范围与指标配置
test(video): 补充端点缺失与负增量用例
```

## 类型与范围

- `feat`：新增功能或用户可见的能力。
- `fix`：修复错误或不符合既定需求的行为。
- `doc`：文档、规范及规范页的说明文案；统一使用单数 `doc`。
- `refactor`：调整结构或复用代码，不改变既定功能。
- `style`：代码格式、空白等不影响行为的调整；有实际视觉效果的 UI 改动按用途使用 `feat` 或 `fix`。
- `test`：新增或调整测试。
- `perf`：性能改进。
- `build`、`ci`：分别用于构建 / 依赖配置、持续集成流程。
- `chore`：不属于以上类型的维护工作；`revert` 用于撤销既有提交。

`scope` 指主要受影响的功能或模块，例如 `video`、`producer`、`overview`、`navbar`、`ui`、`frontend`、`backend`、`sql`。选用已有、容易理解的范围；跨前后端的同一视频功能可统一使用 `video`，不必为每个目录拆一次提交。

## 拆分与提交内容

一个提交完成一项可独立理解和审阅的改动。同一功能的接口、前端、必要测试与文档可以一起提交；无关功能、单独的导航适配、其他 Agent 的独立工作应分开。多 Agent 同时编辑时按文件或改动块选择暂存内容，不使用整仓暂存把未确认归属的改动混入当前提交。

提交前检查工作区与暂存差异，确认标题与实际内容一致，不包含本地密钥、环境配置或构建产物。正文按复杂度补充原因、最终行为及必要的验证结果；简单改动不强制填写模板。测试未执行或仍有失败时如实说明，不能把已有通过记录描述为当前改动已通过。

遵循[验收方式](../../.cursor/rules/verification.mdc)：完成与改动相称的代码检查、测试或构建；常规前端视觉验收由用户手动完成，不以等待手动验收为由中断已授权的提交。仅文档改动检查内容、链接和差异即可；规范页 JSX 文案有改动时检查前端构建。

提交完成后报告提交号与中文标题，说明工作区是否仍有剩余变更。提交与推送分别处理；「提交」不默认包含推送或发布。
