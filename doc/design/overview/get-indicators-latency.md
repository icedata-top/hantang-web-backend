# Overview 指标接口耗时诊断

日期：2026-10-20。接口：`POST /overview/get-indicators`。

这次测量对应筛选区间 `2026-10-13` 至 `2026-10-19`（7 天）。总耗时 **28573 ms**。以后重构 Overview 时，先按查询成本决定页面上放哪些指标、哪些对比，再写接口。指标卡片不能先按展示需求定口径，再让后端在请求里现算。

## 结论

23 秒花在同比区间 `2025-10-13` 至 `2025-10-19` 的 `processed_videos` 聚合上。这条语句同时计算新投稿 `COUNT(*)` 和活跃创作者 `COUNT(DISTINCT user_id)`。

当期同一条语句是 596 ms，环比是 1369 ms。播放、收藏的按天合计每次都不超过 800 ms。当前这一周的活跃创作者数本身不是这 30 秒的来源。

## 一次请求在算什么

`OverviewService.getIndicators` 对三个等长区间各算一遍：

| 窗口 | 本次区间 | 用途 |
|---|---|---|
| `current` | 2026-10-13 .. 2026-10-19 | 指标当前值 |
| `dod` | 2026-10-06 .. 2026-10-12 | 环比，紧挨着的上一个等长区间 |
| `yoy` | 2025-10-13 .. 2025-10-19 | 同比，去年同一日历区间 |

每个窗口 3 条 SQL，串行执行，一共 9 条：

1. `hantang_dynamic.processed_videos`：`pubdate BETWEEN` 起止 Unix 秒，一次算出 `COUNT(*)` 和 `COUNT(DISTINCT user_id)`。对应新投稿、活跃创作者。日志字段是 `processedVideosMs`。
2. `hantang_dynamic.video_daily`：`record_date = 区间开始日`，`SUM(view)`、`SUM(favorite)`。日志字段是 `dailyStartMs`。
3. `hantang_dynamic.video_daily`：`record_date = 区间结束日的次日`，同样两项合计。日志字段是 `dailyEndMs`。播放、收藏增量是第 3 条减第 2 条。

## 实测

日志来自 `OverviewService` 里对上述三段的 `System.out.println`。

| 窗口 | processedVideosMs | 新投稿 | 活跃创作者 | dailyStartMs | dailyEndMs | 小计 |
|---|---:|---:|---:|---:|---:|---:|
| current | 596 | 2,451 | 1,886 | 642 | 21 | 1,259 |
| dod | 1,369 | 2,998 | 2,354 | 593 | 607 | 2,569 |
| yoy | 23,348 | 69,217 | 46,994 | 769 | 609 | 24,726 |
| 合计 | 25,313 | | | | | 28,554 |

三段小计 28554 ms，接口 `totalMs` 28573 ms，差 19 ms，时间都在这 9 条 SQL 上。同比的 `processedVideosMs` 占接口总时间的 82%。

去年同一周的命中行数大约是当期的 28 倍（69217 / 2451），耗时大约是 39 倍（23348 / 596）。两个区间都是 7 天，慢的原因是去年这段命中的行更多，而且这条语句要在命中行上做去重。本次没有跑 `EXPLAIN`，执行计划还没记录。69217 行用了 23 秒，按行数看远慢于一次内存聚合，下一步应看 `pubdate` 条件和 `COUNT(DISTINCT user_id)` 的计划，确认是索引范围扫描、整表扫描，还是冷数据 IO。

## 重构约束

默认打开概览页时，接口同步路径里不要现算去年区间的 `COUNT(DISTINCT user_id)`。这次就是这个计算把首屏拖到 28 秒。

页面上每增加一个「任意日期区间 + 去重人数」的对比，就要单独估一次这个区间的扫描成本。环比、同比都是额外的整段扫描，不是把当期结果再除一次。

活跃创作者不能由「每天的去重人数」相加得到。一周的 `COUNT(DISTINCT user_id)` 小于等于七天日去重之和。预聚合如果只存每日创作者数，无法还原页面上的区间创作者数。新投稿数、播放增量、收藏增量可以按天相加或按天相减。

播放和收藏可以继续按 `video_daily` 的单日合计现算。这次 6 次单日合计合计约 3.2 秒，单次不超过 800 ms。它们不是 30 秒的主体。

新投稿和活跃创作者目前绑在同一条 SQL 上。日志里的 `processedVideosMs` 不能拆成「只慢在去重」或「只慢在计数」。要分开优化这两项时，需要分别计时，或看执行计划里两个聚合节点的耗时。

趋势、分区投稿、播放直方图、门限表不在这次测量里。重构指标卡时不要假设那些接口已经很快；其中按 `pubdate` 对 `processed_videos` 做 `COUNT(DISTINCT user_id)` 的趋势，和这次同比是同一类查询。
