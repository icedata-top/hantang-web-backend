# UniSeek 技改复盘：每日生成 ADM 歌曲搜索宽表

整理日期：2026-11-04。范围：歌曲搜索的数据准备、在线读取、缓存、部署问题及响应样本。设计细节见 [ADM 子设计](adm-search-snapshot.md)，操作入口见 [SQL 使用说明](../../../sql/adm_uniseek_videos.md)，剩余事项见 [TODO](../../todo/uniseek-adm-search-snapshot.md)。

## 结果与依据

开发者已在业务库完成 `hantang_dynamic.adm_uniseek_videos` 的首批构建，并确认 Java 搜索使用新表。歌曲关键词及 AV/BV 查询直接读取同一已发布搜索集，在线不再关联原始视频表与 Daily，也不再探测 Daily 最新日期。首批截图客户端显示 **72,992 行**。

聊天中保留的响应记录如下，本次整理没有重新运行旧逻辑或访问业务数据库：

- **迁移前首次搜索约 3–4 秒**：此前聊天记录中的热门二字词、应用结果缓存未命中样本。
- **迁移前日期定位约 512 ms**：此前一次最新有数据日定位的子步骤耗时，包含元数据查询；不能与整次搜索响应相加或直接作为其对照。
- **迁移后首次视频响应约 700 ms**：开发者使用新表搜索后的反馈。
- **迁移后第二次及后续下滑响应约 100 ms/次**：开发者在同次搜索中滚动翻页的反馈。
- **迁移前后续翻页耗时未单独留存**，没有可比较的旧值。

按首次响应样本粗算，`3–4 s ÷ 0.7 s` 约为 **4.3–5.7 倍**，耗时减少约 **77%–83%**。这些数值来自不同时间的聊天记录，缺少统一关键词、样本次数、测量位置和负载条件；“首次”指该次搜索首次请求，未证明 PostgreSQL 缓冲区处于冷态。迁移同时改变了收录门槛和短词标题召回，因此这里只记录已观察到的体验改善，不作为严格的同条件性能归因或 P50/P95。

后续约 100 ms 与当前实现的缓存复用方式一致：同关键词、同发布 UUID、60 秒有效期内复用已经排序的结果，每页仍检查批次并完成分页和响应。该耗时包含应用及请求链路，不能当成单条 SQL 的执行时间，也不能推导为每次重新扫描宽表只需 100 ms。

## 开发者提出的方向与完成的操作

宽表化的核心方向由开发者提出：**业务只关心有一定流量的投稿，将资格过滤和 JOIN 移到每日任务，在线从更小、已冗余指标的搜索表查询**。Codex 将这一方向补充为可执行、可验证的实现。

开发者定义了业务范围与约束：

- 提出每日通过 CRON 关联歌曲与 Daily，将收录门槛从在线的点赞数 > 10 提高为所选数据日的 **> 100**，冗余播放、收藏、点赞等指标，减少在线 JOIN。
- 用非生产用途的 `video_daily_latest` 做容量评估，反馈 > 100 赞约 **23.78 万行**；随后明确正式同步必须使用 `video_daily WHERE record_date = D`。
- 确认暂时没有上游完成状态表，选择**显式确认日期**，而不是直接把 MAX 日期视为已完成批次。
- 要求 SQL 由自己手动执行；遇到扩展创建权限限制后，明确要求不使用 `pg_trgm`。
- 保持既有搜索交互要求：歌手、创作者、歌曲独立返回，按到达顺序展示，后续只分页加载歌曲；这些交互在宽表迁移前已实现，本次继续沿用。

开发者承担了业务环境中的执行和反馈：

- 连接业务数据库，执行建表与数据构建操作；反馈安装阶段的扩展权限、缺表报错，随后确认表及首批内容已完成，并提供 72,992 行截图。
- 在 Java 实际运行时发现建表账号与应用账号不同，提供 `app_icedata_web` 及 `permission denied for table adm_uniseek_videos`，推动补齐应用只读授权说明。
- 在应用使用新表后手动搜索、滚动翻页，反馈首次约 700 ms、后续约 100 ms 的响应样本。聊天未记录具体授权命令的执行回执，也未确认 CRON 注册及连续每日运行状态。

## Codex 补充、完善与开发的内容

Codex 负责 SQL、应用代码、回归及文档交付，未代替开发者在业务库执行安装、授权或注册 CRON。

数据准备与发布：

- 将方案落实为普通 ADM 表和单行发布控制表，保留 aid/BV、标题、封面、投稿时间、UID、标签/分词/歌手数组、累计指标和来源日、批次 UUID、刷新时间。
- 提供日期确认函数、刷新过程、无空行安装版、特定中断状态的续装版和跨库 CRON 调度 SQL；移除 `pg_trgm`，保留主键、唯一约束及原生数组 GIN。
- 对固定 D 一次准备 Daily 快照，再 INNER JOIN 静态表；保持 `is_deleted = false`，过滤 D 日点赞数 > 100，不凭 `is_filtered` 字段名增加业务限制。
- 增加源行数漂移、源日 aid 重复、候选 aid/BV 重复及最少结果数校验；通过事务级互斥锁和控制行锁串行发布。
- 先在临时表准备校验，再在一个事务内 DELETE / INSERT 正式表并更新发布元数据；失败回滚保留旧批次。保留正式表对象，使已有索引与授权持续有效。
- 同日重新确认生成新 UUID，可重算补数并移除失效视频；调度每 10 分钟检查，有新确认才刷新，避免每次调度都重扫 Daily。

在线查询与缓存：

- 将关键词和 AV/BV 两条歌曲查询统一改读 ADM，移除原始表/Daily JOIN、最新日期探测及相应旧辅助代码；未收录编号正常返回空列表，查询失败保持错误响应。
- 恢复一、二字标题子串召回，保留多词全部命中、数组完整元素匹配和字面通配符转义，不扩大到简介检索。
- 对全部匹配项先计算标题档位、长度接近度和有上限的对数播放量加分，再限制最多 1,000 首，按 score、aid 降序稳定排列，保持原分页接口。
- 将 60 秒、最多 16 个键的结果缓存改为按关键词与发布 UUID 区分，每页检查已发布批次，同日重建也能失效。缓存使用实际排序查询返回的 UUID，处理批次探测后发生发布的交错情况。
- 保留 NULL/0、64 位 ID、来源日期与封面输出，沿用歌手本地匹配、创作者独立查询和前端去重。

验证、接入及文档：

- 交付 DAO/Service/HTTP 回归，以及提取实际 DAO SQL 的查询回归；在没有原始视频和 Daily 表的环境验证新路径，避免误留回源依赖。
- 离线 SQL 回归覆盖安装、续装、资格边界、重复数据、同日重算、发布中途失败和回滚；应用回归覆盖缓存过期、容量、批次切换、分页及独立响应。
- 针对独立应用账号补充 schema USAGE、搜索表 SELECT 的最小授权与检查 SQL，不要求应用账号获得刷新、控制表或写入权限。
- 更新根/前端 README、接口说明、数据源约定、子设计和 TODO，区分首批成功、应用运行反馈及尚未核实的每日调度状态。

## 收益、代价与经验

此次改善来自面向实际业务的搜索集：资格筛选和日指标关联在发布前完成，在线请求只处理已收录的小表；指标直接参与排序，缓存继续减少滚动时的重复评分。首批约 7.3 万行是实际构建反馈，23.78 万是早期非生产单表估算；此前约 823 万行的静态表统计也采用不同口径，不能把行数比例直接换算成响应提速倍数。

宽表承担了存储冗余和每日全量刷新成本，搜索资料与指标跟随发布日更新，无法保证源表每次修改立即出现在搜索中。点赞门槛提高也会主动排除低流量视频。标题 ILIKE 仍可能扫描 ADM 小表，扩展权限受限时先用已筛选的数据集验证可用性，后续按实际查询计划决定是否再引入专用检索能力。

这次部署问题说明，**DDL 和首批构建通过后，还需用应用实际身份验收读取权限**。开发者建表账号与 Java 账号不同；部署说明应同时交付建表/刷新角色和在线只读角色的权限边界。每日 DELETE / INSERT 保留正式表对象，授权不随刷新丢失。

单条 SQL 能读取完整发布批次，结果缓存能识别同日重发，但当前页码接口未固定整个翻页会话的批次。跨发布或缓存过期后仍可能出现重复或遗漏，前端去重只能处理重复；固定快照游标、正式相关性函数及 Elasticsearch 仍属于后续工作。
