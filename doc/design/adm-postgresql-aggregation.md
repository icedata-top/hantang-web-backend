# PostgreSQL 日聚合与存量回刷方案

更新：2026-10-26。状态：已生成辅助表及SQL函数/过程，已在独立内存PostgreSQL测试；用户确认核心脚本已部署并完成一次聚合；本Agent未连接业务库，9:00调度尚未注册。

本文取代此前“每页提交、跨进程续跑、三张辅助表”的设计。Java不负责计算、分页或重试；PostgreSQL内按日集合聚合，失败后重算当天。用户已确认正式表、辅助表和核心脚本创建成功，并完成一次单日执行；核心安装所含辅助表索引已随脚本创建，结果表额外索引与COMMENT状态未单独核验。

## 目标与范围

只生成四类结果，组合采用明确白名单：

- `all / total / __all__`：全量总计。
- `all / partition_v1 / type_id文本`：全量旧分区。
- `all / partition_v2 / tid_v2文本`：全量新分区，不处理pid_v2。
- `zhongshu50-v1 / total / __all__`：固定版本中术50总计。

不生成中术50×旧分区或中术50×新分区，不使用所有scope与所有维度的全组合。歌手、uploader、staff延期。

已有结果表：[adm_entity_metrics_daily](../../sql/adm_entity_metrics_daily_draft.sql)，保持现有宽表结构。最多新增一张业务辅助表：[adm_aggregation_task设计](../../sql/adm_aggregation_task_draft.md)。pg_cron自带的cron schema及元数据表是扩展基础设施，不是额外设计的业务辅助表；若限制连扩展表也不得增加，则不适合采用pg_cron。

## 推荐结构

1. 任务表 `hantang_dynamic.adm_aggregation_task`：每个业务日一条当前任务，保存配置、状态、尝试次数和最近错误。
2. 计算函数：读取指定日期数据，生成四类候选结果及校验摘要，不在内部提交事务。
3. worker存储过程：领取一个日期、执行计算、校验、替换结果、记录完成状态或安排有限重试。
4. pg_cron：周期性以顶层CALL调用worker；日常和历史日期进入同一任务表，不创建海量单日cron job。

已生成[任务表DDL](../../sql/adm_aggregation_task.sql)、[函数/过程](../../sql/adm_aggregation_routines.sql)及[无空行安装脚本](../../sql/adm_aggregation_install.sql)，执行说明见[安装与调用](../../sql/adm_aggregation_usage.md)。本阶段不创建扩展、注册cron或增加Java/API/CLI入口。

## 原子性、重算与数据质量

原子单位是“一个业务日的四类结果”。一次尝试中，源数据计算、校验后的精确替换、任务成功状态在一个业务事务内完成。失败时业务结果完全回滚，已有结果保留，不留下某一类新结果或只删除未插入的半成品。

任务领取和尝试次数先独立提交，失败记录也需持久化：这是运维状态，不属于需回滚的业务结果。否则进程每次崩溃都会把次数一起撤销，无法保证重试上限。“无事发生”指ADM业务结果不受失败影响，不指抹掉失败记录。

覆盖重算，不执行“现有值+本次值”。相同输入重算产生相同统计；源数据变化后重算会得到修正值。每次尝试采用新的attempt_id，成功后写入所有结果行的batch_id。断线发生在提交附近时，以任务表成功状态与batch_id判断；不靠客户端是否收到成功响应推断结果。

任务成功与数据完整分开：SQL计算、校验和发布成功可标记succeeded，但缺快照导致的指标NULL及is_complete=false必须保留。缺快照不是SQL异常，不自动消耗多次即时重试去等待补数；补数后重新排队。

## 单日计算口径

- `record_date`是北京时间凌晨约3±1小时的观测日期。
- D+1快照减D快照归入D日增长；D行累计值取D+1快照。不宣称是严格零点自然日增长。
- 候选集合来自processed_videos，而不是只取有快照的video_daily；所有对象使用统一收录规则，投稿时间早于D+1北京时间00:00。
- 将D和D+1快照按aid左关联到同一集合后逐aid计算。分区NULL归入__unknown__，各自参与旧、新分区对账。
- 七项指标各占累计列和增量列。相减前转换bigint，允许负值；合计溢出明确失败，不截断。
- 当前严格缺失策略沿用表文档：某指标的任一期末成员值缺失则该total为NULL；某成员无法计算相邻日差值则该delta为NULL。确认空集合时为0，缺失不变成0。
- end_snapshot_count和delta_covered_count按七项指标整体覆盖计数，不冒充逐指标覆盖率。is_complete还必须满足集合与口径校验。
- 新投稿缺期初快照不自动补零，除非已确认采集边界与基线规则。旧视频补收录不得用零基线。缺D快照影响D-1和D增量。
- 用户已确认排除is_deleted=true，不依据is_filtered过滤。当前实现对缺投稿时间明确报错；D+1凌晨投稿不属于D日集合，新投稿缺期初不补零，均在执行说明中标明。

严格缺失策略在全量视频中可能经常产生NULL。是否另行展示部分合计及覆盖提示属于待讨论的产品与口径变更，不在本方案静默更改。

## 源数据一致性与聚合SQL

不再冻结输入到持久化表。建议一次源数据SELECT通过CTE完成候选集合、相关重复数据诊断、D/D+1关联、逐aid差值和全部分组。所有源数据读取及诊断来自该语句同一快照，避免默认READ COMMITTED下多条查询读取到不同版本。

全量总计和两套分区可使用 `GROUPING SETS ((), (type_id), (tid_v2))`。用GROUPING标识区分“总计行”与“真实NULL分区”，不能仅靠分区列是否NULL判定。中术50从同一基础集合按固定aid名单另算一个total，以UNION ALL合并；不对样本做分区分组，也不生成旧分区×新分区组合。

计算函数可把少量聚合结果与诊断摘要返回给PL/pgSQL变量，例如结构化数组或JSONB；不是把逐视频明细放进变量。后续校验和写入只消费这份结果，不再次读取源表。无需新建临时表或持久化中间表。若实施改成多条源查询，必须显式采用一致快照事务并验证worker调用方式，不能直接依赖默认隔离级别。

校验相关aid在processed_videos中的唯一性及D/D+1快照的唯一性；发现重复且无法按可靠版本消歧就失败，不用MAX或最终COUNT DISTINCT掩盖指标重复累计。样本50个ID唯一性、元数据缺失、投稿时间和样本版本必须校验。历史日期在样本某作品投稿前不应虚构该作品；应明确按该日集合统计，并报告样本有效成员数。

正式替换前检查两条total存在、目标键唯一、分区计数各自与全量一致；指标对账只有在全量及所有相关分区值完整时才有意义，不让SUM忽略NULL后声称完整对账。

## 唯一辅助表与并发策略

任务表按业务日唯一，一行代表当天的当前执行请求。保存attempt_count、max_attempts、next_attempt_at、状态、统计配置、当前attempt_id、最近错误和结果摘要，不保存视频明细、页游标或中间指标累计。终态任务可显式重排以回刷；正在运行的任务不允许被覆盖配置。

一期只允许一个worker处理业务任务。worker首先尝试获取约定的会话级advisory lock；拿不到就退出，不消耗尝试次数。这把锁必须跨越领取、计算、结果提交这些事务，并在结束时释放。pg_cron为每次执行提供独立连接，连接结束也会释放会话锁；不要把该worker放在未正确释放会话锁的连接池会话里。

所有写ADM的路径必须遵守此互斥约定。pg_cron只保证同一个cron job不重叠执行，不保证不同job或其他调用互斥，因此仍保留数据库锁。

采用一个全局worker意味着同一时刻只计算一个日期，以减少并发、陈旧任务和租约处理复杂度。日常任务可优先于历史回刷，其他同优先级日期按顺序处理；若将来有必要并行，需要重新设计，不预先引入多worker。

## worker事务流程

建议worker为不带外部BEGIN包裹的顶层CALL存储过程，正常每次最多处理一个日期：

1. 获取会话互斥锁。若存在遗留running，获得全局锁说明没有其他遵守约定的worker仍在执行；将其按已消耗次数恢复为retry_wait或failed，不直接当成功。
2. 锁定一个到期的pending/retry_wait任务，确认attempt_count<max_attempts，创建attempt_id、次数加1、设为running并提交。这是领取事务。
3. 开始本次计算及发布：检查任务与attempt_id仍匹配，计算候选结果并校验，精准删除该日四类旧结果，插入新结果，标记succeeded。结果和成功状态同一事务提交。
4. 可捕获的异常使用PL/pgSQL异常块回滚本次业务修改，块外保存错误SQLSTATE/消息与下次重试时间或failed状态，再提交。COMMIT必须位于异常子事务块之外，不能在函数内部或异常块中随意提交。
5. 正常结束释放会话锁。连接断开、后端退出、取消或重启等无法正常收尾时，未提交业务写入回滚，已提交尝试次数保留；会话结束释放锁。下一worker按第1步恢复。

领取后的系统级异常也可能使任务停在running。不能只靠异常处理器保证恢复，也不能在旧worker仍持有全局锁时强行重新领取。连接长时间未结束时由查询/锁等待超时和运维终止处理，不额外引入需要续租的租约机制。

捕获错误后返回正常的worker调用可能在pg_cron执行日志中显示“成功”，而业务任务为retry_wait/failed；监控以任务表业务状态为准，同时保留数据库异常信息。pg_cron执行状态不等同于聚合成功。

## 重试上限

max_attempts表示总尝试次数，候选默认3，即首次加两次重试；具体次数与退避间隔可配置。只有实际领取才加次数，空队列、锁忙不计入。

可重试如死锁、序列化冲突及明确暂时故障；数据重复、非法名单、规则错误等直接failed，修复后显式重排。超时不默认无限重试；需评估是否只是查询成本过高。每次重试从新快照完整重算D，不恢复上次执行中的进度。

连接/进程故障发生时错误详情可能无法保存，但领取次数已提交，不会无限免费重试。次数耗尽后进入failed，不自动新增同日任务绕过限制。日常入队也不得每次重置失败任务次数。

## 存量回刷和日常聚合

两者共用任务表和计算函数。存量回刷将闭区间[start_date,end_date]展开成每日任务，不把全年装进一个事务，也不为每一天创建独立cron job。单日成功保留，失败日期有限重试。

入队动作必须幂等：普通补齐只补不存在的日期，不重置running/failed/succeeded任务；明确要求重新计算时，只对允许重排的终态任务生成新执行请求并重置次数，且记录新的配置。区分“补齐缺日期”和“强制重算已存在结果”。

日常聚合在D+1采集窗口结束且具备可用输入后安排D；调度采用北京时间09:00，相对约04:00采集窗口预留约5小时；这不是采集完成证明，缺失仍如实记录。可以后续设置短窗口回看，修复迟到快照。快照D补齐时重排D-1与D；收录和分区修正按影响范围重排历史。

中术50名单当前只在Java JSON资源中。建议将经过验证、排序后的50个aid与sample_scope一起保存到任务行，数据库计算不再依赖Java运行时。相同sample_scope必须对应同一名单；入队/执行需核验已保存任务的同版本配置一致性。换名单使用新scope，不将版本随意拼接。名单导入与版本发布方式待实施时确定。

精准替换仅影响D日的all/total、all/partition_v1、all/partition_v2及当前sample_scope/total。不删除其他样本版本、未来维度或其他日期。两条total与所有分区行共享本次attempt_id作为batch_id及definition_version。

回刷整个区间不是全区间原子切换；同一统计规则版本下逐日发布。若修改规则或样本后产品要求整个历史同时切换，现有表只覆盖规则版本而不保留多版本结果，需另行设计；本期不承诺该能力。

## 部署与性能前提

- 核实目标PostgreSQL版本、PL/pgSQL过程事务支持、pg_cron可用性、shared_preload_libraries配置及必要的重启权限。pg_cron是扩展，不是核心自带的cron。
- 以实际库名调用worker，不把hantang_dynamic误当数据库；业务对象均使用该schema限定名。
- 配置cron时区为Asia/Shanghai，同时业务日期转换显式指定时区。用户确认北京时间09:00首次处理；此后每5分钟唤醒处理重试/存量队列，09:00前直接返回。执行[调度增量更新](../../sql/adm_aggregation_schedule_update.sql)后，用[启用SQL](../../sql/adm_aggregation_schedule_enable.sql)注册；本次不连接服务器注册。
- 第一阶段只注册一个受控调度周期任务即可；SQL只允许固定聚合逻辑，不存储任意待执行SQL命令。
- 核实processed_videos(aid)唯一约束、video_daily(record_date,aid)唯一/查询索引及ADM辅助索引。仓库字段快照不含索引，不能假设线上已有。
- 单日事务仍会扫描该日相关视频，源数据体积和索引决定耗时。用数据库GROUP BY避免Java传输，并不意味着迁入函数会自动变快。
- 先串行刷一小段历史，测SQL耗时、扫描行数、磁盘临时空间与WAL，再确定任务频率、超时和退避。不在数据库中用长时间sleep等待重试。
- pg_cron执行日志有独立保留策略；业务任务表仅保留当前状态与最近错误，不再为每次尝试建日志表。
