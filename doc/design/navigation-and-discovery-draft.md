# 总览、分类列表与详情页：产品讨论草稿

日期：2026-10-21

> 状态：讨论草稿。本文仅记录本次讨论中的方案、倾向与待确认问题，不是最终 PRD、正式需求、开发任务或验收依据。文中的页面内容、筛选项、排序和推进顺序均为候选建议，尚未确认实施；不代表当前系统已支持这些功能。

## 背景与讨论前提

最初讨论了两种方向：

1. 在总览页加入虚拟歌手、创作者的多选筛选。
2. 总览页主要保留日期范围，将具体对象的数据查询放到对应页面。

用户明确的产品设想是：歌曲、虚拟歌手、创作者都会有详情页，例如《普通DISCO》、洛天依、ilem 的详情页；这些对象之间能够通过关联信息相互跳转。全局搜索结果页也在设想中。

最初认为虚拟歌手可能有列表页，歌曲和创作者主要通过搜索进入。进一步讨论右上角的「歌曲 / 虚拟歌手 / 创作者」菜单后，提出为三类对象都提供可直接浏览的列表页。

## 当前方案倾向

如果保留上述三个顶级菜单，建议分别进入对应的列表页。页面在没有搜索关键词时也展示内容，并提供合理的默认排序；不要求用户先知道对象名称。

页面职责暂按以下方式理解：

- 总览页：观察全局变化与趋势。当前已有中术50等特定样本指标，实际展示范围仍须按各指标口径标注，不能把所有数据都理解为全曲库统计。
- 分类列表页：浏览、发现对象，并通过筛选和排序缩小范围。
- 详情页：深入查看一个对象的数据、趋势、相关作品与关联对象。
- 全局搜索及结果页：查找已知对象，快速进入详情页。

列表与搜索结果可复用展示组件，但入口和默认内容不同。仅查看某一个对象的数据，详情页通常已足够；列表页的价值在于发现和筛选。

## 总览页的筛选讨论

当前倾向是主要保留日期范围，暂不因为“筛选项太单薄”而增加虚拟歌手和创作者多选。

多选涉及两种不同需求，需要分别验证：

- 范围筛选：例如将洛天依和乐正绫相关作品圈定为一个集合，查看去重后的汇总表现。
- 对象对比：例如分别展示洛天依和乐正绫的指标与趋势，比较增长差异。

多选后合并数据不能替代对象对比。后续若确认对比需求，可探索详情页「加入对比」或搜索中选择多个对象等入口；这些均为后续候选，不纳入已确定范围。

若未来增加总览多选，需要先确定同类对象间、跨类型对象间的并集或交集规则，以及多人合作、多歌手作品的去重和归属口径。例如同时选中「洛天依」和「ilem」，究竟表示二者合作作品，还是所有相关作品，目前未定。

## 三类列表页的候选内容

### 歌曲页

定位为可筛选、可排序的作品库，无关键词时也展示歌曲列表。

- 默认排序可考虑近期热度；其他候选包括最新投稿、累计播放。热度定义和最终默认排序待定。
- 每条候选信息：封面、歌名、虚拟歌手、创作者、投稿日期和少量核心指标。
- 候选筛选：投稿日期范围、虚拟歌手、创作者。后两项可采用支持搜索的多选组件。
- 点击歌曲进入详情页，关联歌手和创作者可跳转至对应详情页。

这里适合承接“浏览若干歌手或创作者相关作品”的需求，但作品列表筛选不等同于对所选对象进行汇总分析。

需要区分两种时间条件：

- 投稿日期：限定哪些歌曲进入列表。
- 统计周期：决定查看哪个时段的播放、增长等表现。

若初期只展示累计指标，可先仅提供投稿日期筛选；若支持“近七天播放增长”等排序，再明确统计周期及其与投稿日期的关系。

### 虚拟歌手页

定位为偏发现和比较的歌手目录，无关键词时可浏览全部歌手。

- 数量较少时可采用卡片，具体形式待确认。
- 候选信息：头像、名称、作品数和核心指标。
- 候选排序：热度、作品数等，具体口径待定。
- 点击进入歌手详情页，再查看相关作品和创作者。

初期不必堆叠筛选条件，优先让用户识别熟悉的歌手并发现其他歌手。

### 创作者页

定位为可搜索、可浏览的创作者目录，无关键词时也提供内容。

- 创作者数量可能较多，可优先考虑信息紧凑的列表。
- 候选信息：名称、创作角色、作品数、代表作和核心指标。
- 若角色数据可靠，可探索作曲、作词、调教等角色筛选；同一创作者可具有多个角色。
- 默认排序可考虑近期活跃或近期作品表现，避免累计指标使头部长期占据曝光；最终规则待定。
- 点击进入创作者详情页，关联作品和虚拟歌手可继续跳转。

角色、代表作等信息是否完整可靠，尚需核实。本草稿不将上传者账号直接等同于作品的全部创作者，具体实体关系仍待定义。

## 详情页与关联浏览

详情页的候选能力包括日期范围、核心指标、趋势、相关作品或关联对象。具体模块、指标及布局尚未讨论确定。

候选浏览路径包括：

- 全局搜索 → 对象详情。
- 分类菜单 → 列表筛选或排序 → 对象详情。
- 歌曲详情 → 虚拟歌手或创作者详情。
- 虚拟歌手或创作者详情 → 相关歌曲详情。

这些路径用于说明页面之间的关系，不构成路由或交互规格。

## 候选推进顺序

1. 明确三类对象的身份、关联关系和数据口径，以及顶级菜单与列表页的对应关系。
2. 完善搜索、详情页和关联跳转；列表页可从轻量版本开始，优先考虑歌曲页的浏览与筛选。
3. 根据实际需求决定是否增加对象对比，以及总览页的对象范围筛选。

以上仅为讨论中的推进建议，不代表已排期或承诺交付。

## 后续需要确认的问题

- 是否最终保留三个顶级菜单，并为三类对象分别建设列表页？
- 各列表默认排序、可选排序和核心展示指标是什么？近期热度、近期活跃如何定义？
- 歌曲与视频的映射如何处理？同一歌曲的多个投稿版本如何展示和计数？
- 创作者与上传者如何区分？合作角色及归属数据是否足够支持筛选与统计？
- 多选筛选采用何种集合规则？合作作品如何去重、归属和汇总？
- 日期条件作用于哪些内容？哪些地方需要投稿日期，哪些地方需要统计周期？
- 用户更需要多个对象的汇总，还是分别对比？是否值得增加独立对比能力？
- 哪些指标可以在合理查询成本下提供？需结合现有[总览接口耗时诊断](overview/get-indicators-latency.md)评估，不能由界面设想直接推导实现可行性。

在这些问题确认前，本文保持讨论草稿状态，不据此直接实现全部候选功能。
