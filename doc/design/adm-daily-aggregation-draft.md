# ADM 日粒度聚合方案与评估（草案）

日期：2026-10-21。

> 本文及配套 DDL 仅供方案评估，不是最终 PRD、已批准需求或自动迁移。用户评估后自行手动建表。本次没有连接数据库、执行 DDL、写入数据或改动现有接口。

## 第一期范围更新（优先于下文早期讨论）

本期仅生成以下四类结果，配套 DDL 已按此收敛：

- 全量总计：`scope_key=all`、`dimension_type=total`、`dimension_key=__all__`。
- 中术50总计：如 `scope_key=zhongshu50-v1`、`dimension_type=total`、`dimension_key=__all__`；样本版本标识须与实际名单对应。
- 全量旧版分区：`scope_key=all`、`dimension_type=partition_v1`、对象键为 type_id 的文本形式。
- 全量新版分区：`scope_key=all`、`dimension_type=partition_v2`、对象键为 tid_v2 的文本形式。不处理 pid_v2。

虚拟歌手、uploader、staff 均暂缓；作者未来按 uploader 和 staff 身份分别支持，不以统一 creator 替代。新增类型时修改 CHECK 约束即可复用表结构，不预先生成空聚合行。旧版与新版分区分别独立聚合、独立对账，不跨两套分区相加。

七项指标的累计值和增量均保存。record_date 是观测日期，通常北京时间凌晨3±1小时；用户确认 D+1 快照减 D 快照归入 D 日增长。为保持同一行时间对齐，D 行的累计值定义为 D+1 快照合计，并非 record_date=D 的快照。它是快照观测区间，不宣称精确的零点至零点增长。D日集合按D日结束前已投稿定义，因此排除D+1凌晨新投稿的视频；这些视频的采集边界贡献如何归入投稿日，仍需ETL明确，不能擅自跨日补算。

歌手字段当前没有有效数据。统一收录规则仍待确认，不能猜测 is_filtered 的含义。缺失快照常见；现有 DDL 保留覆盖计数、可空指标和完整标记，允许如实记录缺失，不将缺失变为0。缺失D快照会影响D-1和D的增量。逐指标覆盖率、插补策略及是否展示部分合计尚未确定；当前严格策略为不完整的指标返回NULL，不进行插补。

下文歌手、创作者及候选方案属于此前讨论背景，不扩大本期范围。

## 结论

赞同把歌曲逐日明细预聚合为歌手、作者、分区和总计的日数据，供看板查询。对目前相同指标、相同日粒度、以单对象趋势和同类对象排行为主的访问方式，推荐一张宽指标聚合表，用维度类型和对象键区分结果。

更准确地说，这是一张“日粒度一致、汇总对象不同”的表，不混入月、年粒度，也不混入任意歌手×作者×分区的组合。相比每个维度各建一表，统一表更容易复用趋势、汇总和排行榜查询；相比指标名/指标值的长表，宽表能直接用明确类型读取固定的七个指标。

它可以归入项目约定的 ADM 应用数据层。使用现有 PostgreSQL schema `hantang_dynamic`，表名为 `adm_entity_metrics_daily`，通过 `adm_` 前缀标识应用聚合层，不新建 schema。若将来指标差异大、实体级数据量或维护周期明显不同，再考虑拆表；单表不是所有看板场景都最优。

## 现有代码和字段提供了什么依据

- `sql/hantang_dynamic_schema.sql`：`video_daily` 以 `record_date`、`aid` 及播放、收藏、点赞、硬币、分享、评论、弹幕七个指标保存明细。字段快照未包含主键和索引，不能据此断定线上已保证 `(record_date, aid)` 唯一。
- `OverviewDao` 当前将这些指标作为累计快照，以 D+1 快照减 D 快照计算 D 日增长。这是代码现状，尚未核实真实采集时点是否对应自然日边界。
- `processed_videos` 提供 `pubdate`、上传者 `user_id`、协作者 `staff`、歌手文本标签 `label_singers`，以及 `type_id`、`tid_v2`、`pid_v2`。这些字段还不足以直接认定完整的创作者、角色和历史归属关系。
- 现有分区查询使用 `type_id`；本方案暂沿用，不与 v2 分区混用。
- 总览的播放/收藏及相关趋势目前只统计中术50，新投稿等指标不是同一个样本范围。新聚合不能悄悄把中术50替换成全量数据。
- [已有耗时记录](overview/get-indicators-latency.md)中，主要慢点是日期范围内去重上传者的扫描。日标量聚合不能精确回答任意区间去重上传者数，所以该慢点不能仅靠本表全部解决。

本方案依据仓库字段快照和代码设计，未检查线上数据规模、索引、执行计划、重复记录或缺失比例；不承诺具体毫秒数。

## 一行的业务含义

唯一键为 `(scope_key, dimension_type, dimension_key, stat_date)`。

- `stat_date`：业务日，统一按 Asia/Shanghai。
- `scope_key`：数据范围，如 `all`（按约定纳入的全部视频）、`zhongshu50-v1`（固定版本样本）。不是临时筛选条件，不为用户每次多选生成一个 scope。
- `dimension_type`：`total`、`singer`、`creator`、`uploader`、`partition`。
- `dimension_key`：稳定实体键。总计固定 `__all__`；无归属可以使用 `__unknown__`；其他对象使用规范化实体 ID，统一转为文本。文本是为了兼容当前歌手缺少数值 ID，不建议直接用显示名称当长期主键。

例如同一天、同一个 scope，可以分别有总计行、洛天依的歌手行、某个 UP 主的上传者行、某个分区行。这些行覆盖的明细有重叠，不得跨类型相加。对象名称、头像、简介等保留在实体信息中，不逐日在聚合表重复保存。

保留 `uploader` 是为了准确表达现有 `user_id` 数据。只有上传者数据时先生成 uploader 行；不能用它填入 creator 并对外宣称是创作者统计。creator 行需有确认的作品—创作者映射，且同一人同一视频多个角色只计一次。

## 聚合口径建议

### 先明确统计对象仍是视频

当前可用主键是 aid，因此 `video_count` 和 `submission_count` 暂按视频计算，不命名为去重歌曲数。同一音乐作品的多个投稿仍是多个视频。若产品需要按音乐作品归并，应先建设作品—视频映射，再定义作品层统计。

需要先确认纳入规则：`is_filtered` 的真假含义、`is_deleted` 的处理、无投稿时间视频的处理、收录边界。不能只凭字段名称猜测过滤条件。未知或未纳入视频的计数应在 ETL 校验报告中记录。

### 日集合和历史归属

定义 A(scope, object, D) 为 D 日期末属于该对象、满足收录规则且已投稿的视频集合。同一 aid 在同一集合只出现一次。

V1 建议采用“当前纠正后的归属回溯重算”，因为当前只有现态元数据，没有可靠的历史关系快照。后补的歌手标注可以修正历史图表，但必须重算受影响历史。若需要“当时收录/当时归属”的历史观察口径，必须补充带生效时间的关系和收录历史；本表本身无法恢复它们。

历史期末集合仍须满足投稿时间不晚于 D 期末，不能把尚未投稿的视频放入历史总量。新发现的旧视频可能导致历史指标回算，需向产品解释。

### 七个指标同时保存期末累计与当日增量

对 view、favorite、like、coin、share、reply、danmaku 分别存储 `*_total` 和 `*_delta`，全部使用 bigint，不按源明细 integer 累加。

在“D 为期初快照，D+1 为期末快照”的待确认假设下：

```text
metric_total(D) = Σ metric(aid, D+1)，aid ∈ A(D)
metric_delta(D) = Σ [metric(aid, D+1) - baseline(aid, D)]，aid ∈ A(D)
```

必须先逐 aid 对齐再求差，不能直接对两个成员不同的日汇总相减。元数据归属变化、补收录或成员缺失会使后者把存量变化当成增长。

- total 是期末存量，只取某日期的值，不跨日求和。
- delta 是当日变化，完整连续日期可相加。成员变化时，其区间合计不一定等于两个 total 相减。
- 新投稿的期初可以为零，但只能在确认投稿前不存在且期末观察有效时使用；历史补收录视频不能以零代替缺失基线。
- 不拿“上一条记录”冒充前一天快照；相隔几天的差额不能全算到一天。
- 保留负增量，不做 `GREATEST(delta, 0)`，以免掩盖源端修正或回退；同时在质量报告里提示异常。
- 实际采集若发生于每天不固定时刻，需把结果说明为快照间变化，不能宣称精确的自然日增长。正式 ETL 前必须核实。

### 投稿数和存量视频数

- `video_count`：A(D) 中去重 aid 数，属于期末存量。
- `submission_count`：A(D) 中 pubdate 落在 D 业务日的视频数，完整连续日期可相加。
- 时间归日显式使用 `(to_timestamp(pubdate) AT TIME ZONE 'Asia/Shanghai')::date`，不依赖数据库或 Java 进程默认时区。筛选使用本地日界线对应的左闭右开时间区间。

### 合作视频采用完整归属，接受跨对象不可加

建议 V1 采用完整归属：洛天依与乐正绫合唱的视频，分别完整计入两位歌手；多人合作视频也完整计入每位已确认创作者。同一视频内先去重成员，避免重复标签、多个角色和重复关联造成乘法膨胀。

因此所有歌手或所有作者相加可能大于总计；总计必须独立按 aid 去重聚合。分区若使用单一、互斥的 type_id，且补上未知分区桶，则在相同范围、日期和完整性下可与总计对账。多歌手视频的贡献不是互斥份额，不适合直接制作“合计100%”的歌手份额饼图。

不能在同一次未去重的 JOIN 中同时展开 singer 和 creator 再汇总。应先形成独立的维度成员关系，分别聚合后 UNION ALL 到目标表；或基于经过验证的规范化关系使用等价的分组实现。

### 缺失不等于零

每个指标独立处理：集合内任何成员缺少该指标的期末值，对应 total 为 NULL；任何成员缺少有效基线或期末值，对应 delta 为 NULL。不把“部分成员之和”伪装成完整总量。

集合为空且确认计算成功时，指标应为真实的 0；缺行表示尚未发布，不能当作 0。无标注歌手可进入 unknown 桶，但展示为“未标注”，不能当成真实歌手或真实人物。

`end_snapshot_count` 记录七项期末指标均存在的视频数；`delta_covered_count` 记录七项增量均能计算的视频数，含经证实的零基线。这两个字段只提供整体覆盖诊断，不是各指标的覆盖率。

`is_complete` 仅在集合、关联、投稿日期和七项指标都通过校验时为 true。数据库约束只检查其中可表达的部分，不能证明 ETL 已找齐所有源视频。若只缺一个指标，其他完整指标仍可有值，但 V1 默认看板按整体完整状态展示，避免隐瞒缺口。

## 单表不能回答哪些问题

- 任意日期范围的精确活跃作者/上传者人数：每天去重人数不能相加。建议在需要时使用独立的“对象—日期”活动关系表进行区间去重，或针对固定周/月另算汇总。近似算法必须明确误差，并评估扩展依赖；不在本 DDL 中引入。
- 任意多个歌手或作者作品并集的去重合计：不能直接 SUM 对象行，合作视频会重复。分别对比对象没有此问题；并集统计需回到成员关系和视频日事实，或为明确高频组合另建预计算。
- 歌手 AND 作者 AND 分区等交叉筛选：三个边际聚合无法推出交集，不能先全量预计算所有组合以免爆炸。
- 任意投稿日期范围限定的作品表现：本表没有投稿日期这一额外维度，单个 submission_count 不能还原该范围的视频集合表现。
- 每首歌列表、播放分布直方图和门限事件明细：仍由明细/事件表或专门聚合支持。本表不能替代全部总览接口。

## 查询方式示例

以下仅供评估，日期和对象键为参数示意。每个查询都限定 scope 和维度类型。

单个歌手日趋势（`$1` 为规范化歌手键）：

```sql
SELECT stat_date, view_delta, favorite_delta, video_count, is_complete
FROM hantang_dynamic.adm_entity_metrics_daily
WHERE scope_key = 'all'
  AND dimension_type = 'singer'
  AND dimension_key = $1
  AND stat_date BETWEEN $2::date AND $3::date
ORDER BY stat_date;
```

区间总播放增量：必须校验日期覆盖，不能让 SUM 忽略 NULL 后返回貌似完整的数值。这里采取严格的七项整体完整策略。

```sql
SELECT CASE
         WHEN COUNT(*) = ($2::date - $1::date + 1)
          AND BOOL_AND(is_complete)
          AND COUNT(DISTINCT definition_version) = 1
         THEN SUM(view_delta)
         ELSE NULL
       END AS view_delta
FROM hantang_dynamic.adm_entity_metrics_daily
WHERE scope_key = 'all'
  AND dimension_type = 'total'
  AND dimension_key = '__all__'
  AND stat_date BETWEEN $1::date AND $2::date;
```

API 仍应校验起止日期合法，并同时返回数据状态、缺失日期和已发布截止日。DDL 没有覆盖日期的任务状态表；阶段一可通过总计行连续性校验和外部任务日志管理，不能仅以 `MAX(stat_date)` 认定全部历史完整。

同一天的上传者排行榜：

```sql
SELECT dimension_key, view_delta
FROM hantang_dynamic.adm_entity_metrics_daily
WHERE scope_key = 'all'
  AND dimension_type = 'uploader'
  AND stat_date = $1::date
  AND is_complete
ORDER BY view_delta DESC, dimension_key
LIMIT 50;
```

此榜仅展示完整对象；若部分对象缺失，应在榜单整体提示，不称为无缺口的全量排名。七天榜需先按对象 SUM 日增量，再校验日期连续性和规则版本；大规模区间榜仍有聚合和排序成本，必要时对高频固定窗口额外缓存。

## ETL、回补与一致发布

1. 先校验源 `(record_date, aid)` 唯一性，确认源快照时点；重复时必须按可靠采集时间/版本消歧，不能任意取最大值。当前字段快照没有此排序依据，若存在重复需先治理。
2. 生成统一收录集合及规范化歌手、创作者、上传者、分区关系，避免对每个对象重复扫描原始明细。映射覆盖与无法归属数量进入批次日志。
3. D+1 快照采集完成后计算 D，准备独立暂存结果并完成校验；不是到零点就假定源数据齐备。
4. 同一 scope、同一日的所有类型在一个事务中删除旧结果并插入完整新批次，或使用等价的原子替换。只 UPSERT 新结果会留下已经消失的对象行，必须处理残留。并发任务需对同一 scope/date 串行化。
5. 源明细和关系读取应处于一致快照；正式发布可暂存后短事务替换，避免长时间持锁。一个页面多条 SQL 需要跨查询一致时使用一致读取事务，或约定相同批次检查。
6. `batch_id` 由作业生成 UUID；`computed_at` 只表示计算时间，不当作源采集时间。任务日志另记源水位、异常数量、规则版本及耗时。更新时显式刷新 computed_at。
7. 快照日期 D 修复时，按本方案边界影响 D-1 和 D 的结果；关系、样本、收录规则修复可能影响更长历史，不只重跑最近一天。
8. 历史重算分批进行。相同统计口径以 definition_version 标识，API 拒绝混版本区间或提示重算中；需要整段无缝切换时用影子结果及切换机制，单个日事务不保证整个历史瞬时切换。
9. 中术50样本版本使用独立 scope。版本更换后的历史展示策略须另行确认，不把不同名单的序列直接拼接解释为固定样本趋势。

可以设计定期回看最近若干日以处理迟到数据，具体回看窗口要看采集延迟；历史关系修正仍需按受影响范围定向回补。

## 性能评估与索引

若一天视频明细数量为 N，歌手数 S，创作者数 C，上传者数 U，分区数 P，本表单个 scope 的每日行数约为 `1 + S + C + U + P`（另含少量未知桶）。D 天约乘 D；多 scope 按各自规模累加。若暂不生成 creator 或 uploader 某一种，则不计该部分。

单对象 D 日趋势从扫描大量视频降为读取至多 D 条；总计趋势同理。单日作者榜仍需读取并排序当日作者集合；如果 U 接近 N，压缩收益较小，但查询不再实时做视频—作者关联和指标聚合。准确收益需真实基数和 EXPLAIN 验证。

- 主键 `(scope_key, dimension_type, dimension_key, stat_date)`：服务固定对象的日期范围。
- 辅助索引 `(scope_key, dimension_type, stat_date)`：服务同类对象按日期查询。
- 不为七个指标先建七个排序索引，也不把十四个指标全部塞入覆盖索引。是否增加单日热榜索引或固定窗口缓存，用实测决定。
- 初期采用普通表，不在未知数据量下直接分区。表体积、按月回补/清理和执行计划证实需要后，再按日期分区；迁移需要另行设计，当前 DDL 不包含分区管理。

索引列顺序遵循 PostgreSQL 对 B-tree 前导等值条件及后续范围条件的说明；主键同时保证结果唯一。参考官方文档：[多列索引](https://www.postgresql.org/docs/current/indexes-multicolumn.html)、[约束](https://www.postgresql.org/docs/current/ddl-constraints.html)、[分区适用性](https://www.postgresql.org/docs/current/ddl-partitioning.html)。DDL 不依赖额外扩展；目标数据库的具体版本和执行计划尚未实测。

## 建表前建议确认及后续验证

建表前优先确认：

1. 作者指上传者，还是完整创作者？是否需要两者同时保留？
