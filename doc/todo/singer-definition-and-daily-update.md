# 虚拟歌手定义、视频关联与每日信息更新

状态：待梳理、待实施。日期：2026-10-21。

## 需求背景

当前视频缺少可用的虚拟歌手信息，已有 `processed_videos.label_singers` 字段尚无实际有效数据；同时缺少统一的歌手实体定义。无法可靠判断某视频由谁演唱，也无法生成歌手聚合及支持关联浏览。

需要先完成歌手定义与视频—歌手关系的数据预处理，再支持后续歌手页面和日聚合。它是歌手聚合的前置依赖，不阻塞总计、中术50及两套分区聚合的独立推进。

## 目标与范围

- 定义虚拟歌手实体、稳定ID、标准名称及别名；明确哪些对象纳入“虚拟歌手”。
- 建立视频aid与歌手的多对多关联，支持合唱，去除重复关系。
- 区分未处理、已识别歌手、已确认不含虚拟歌手及待复核等状态，具体状态模型待定；不能让空值承担全部含义。
- 建立每日定时任务，处理新增、缺失信息及需要更新的视频歌手信息。
- 提供存量补全和错误修正能力；记录来源及更新时间，支持追溯和下游重算。

## 候选技术方案

先确认数据源和识别规则，再决定复用文本数组还是建设规范化歌手实体及关系表。聚合应使用稳定ID，不依赖可变名称；现有标签可作为候选输入，不应直接视为权威歌手定义。

每日任务增量处理新增及待补全对象，失败可重试，同一视频重复执行不生成重复关系。人工确认结果、自动识别结果的优先级及复核机制需要明确。具体调度时间、技术栈、识别模型和数据源尚未确定。

关系修正后应能定位受影响的视频，供后续歌手日聚合定向重算。每日任务负责更新歌手信息，不在本待办中提前实现歌手统计聚合。

## 卡点与待确认问题

- 歌手身份边界：角色、声库、不同语言/版本/形态是否视为同一实体？
- 标准歌手名单和别名的来源，以及维护责任。
- 视频歌手信息来自何处，如何区分真实演唱、标题提及和非演唱标签？
- 识别冲突、不确定结果和人工修正如何处理？是否有可用于质量验证的人工样本？
- 现有label字段与未来实体关系如何兼容；存量规模、数据源限制和每日处理预算是多少？
- 每日任务由哪个系统运行，何时运行，失败如何记录与补跑？

## 验收与验证

- [ ] 歌手定义、稳定标识和别名映射有明确说明及维护方式。
- [ ] 单歌手、合唱、别名和无法识别等样本处理符合约定，关联不重复。
- [ ] 未处理和已确认无虚拟歌手能够区分，不将未识别误判为不存在。
- [ ] 每日任务可定时运行、幂等重试，并能观察处理数量、失败和待复核记录。
- [ ] 存量信息可补全，修正可追溯，并能提供后续聚合所需的受影响视频范围。
