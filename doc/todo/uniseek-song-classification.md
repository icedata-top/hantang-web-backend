# UniSeek：投稿三维打标与后续创作者识别

创建日期：2026-11-06。状态：方案已记录，待实施；尚未确定最终字段、模型、提示词及账号筛选阈值。

## 背景与目标

UniSeek 当前收录集中包含舞蹈等非歌曲视频，不能直接把收录投稿视为中V歌曲，也不能把所有已发现账号视为中V创作者。用户估计首批待处理投稿约为20万量级，实际规模应在实施时按当前数据核实。

先在投稿粒度分别标注三个独立维度：**是否歌曲、演唱来源、演唱语言**。基于这些标签组合出中文虚拟歌手歌曲集合，并预留未来日语虚拟歌手业务。投稿打标稳定后，再聚合账号数据识别UP主。

本阶段按内容判断，**搬运的歌曲也是歌曲**，无需判断上传者是否原创、是否参与创作，也不把创作归属作为歌曲收录前提。

## 已确认的业务口径

### 1. 是否歌曲：判断视频主体

- 标注视频的主体是否为歌曲作品展示，不能仅凭视频中存在歌声或歌曲BGM判断。
- 歌曲本体及以歌曲为主体的MV可以纳入。
- 舞蹈视频即使用了中V歌曲作BGM，也应排除出歌曲投稿集合；其他以歌曲为配乐的非歌曲视频遵循相同原则。
- MMD等表现形式应按视频主体判断，不能仅凭形式名称一律纳入或排除。
- 保留“是／否／不确定”；资料不足时不强制判断。

### 2. 演唱来源：判断是否符合虚拟歌声口径

- 识别实际演唱来源，区分虚拟歌手、真人演唱、AI拟声，以及混合或不确定的情况。
- 真人演唱、VUP本人演唱、AI拟声不纳入目标虚拟歌曲集合。虚拟形象、角色名或账号身份本身不能证明使用了虚拟歌声。
- 真人与虚拟歌手合唱保留混合信息，最终收录政策待定，不强制归入纯真人或纯虚拟歌声。
- 允许使用外语声库演唱中文；声库身份不替代演唱语言判断。
- AI拟声与目标歌声合成声库的操作性边界需在实施前写入标注规范，不能只凭名称中是否出现“AI”决定。

### 3. 演唱语言：独立且允许多值

- 按实际演唱语言标注，例如汉语、日语、英语；多语歌曲允许同时保存多个语言标签。
- 中文标题、中文简介或中文标签不能直接证明实际演唱语言为中文。
- 语言与声库归属独立：外语声库唱中文可进入中V集合；中文声库唱日语可进入日语虚拟歌曲集合。
- “无语言”与“无法判断”分开，不能相互替代。
- 汉语方言、少量外语段落、哼唱等情况的标签粒度及收录政策待定。

## 派生收录规则

三个维度独立保存，业务资格由明确的规则组合，不把所有信息压缩成一个永久的“中V／非中V”字段。

- **中V歌曲**：确定是歌曲、符合本站虚拟歌声口径、演唱语言包含汉语。
- **日语虚拟歌曲**：沿用上述规则，将目标演唱语言换成日语。
- 多语歌曲的标签可以复用；是否在多个业务集合同时收录，以及混合真人演唱的处理方式，需固定政策后再上线。
- 不确定的投稿进入待复核集合，不能自动当作“否”，也不能按半个正例参与后续账号统计。

这里预留的是按演唱语言组织业务的能力。未来如需按声库、角色或其他归属筛选，可增加独立信息，不改写已有语言标签的含义。

## 建议的数据与推理方案

以下为实施建议，字段名、表结构与模型选型尚未冻结。

- 视频静态信息统一使用 `hantang_dynamic.processed_videos`。离线读取标题、标签、简介、分区等信息，不仅依靠标题；现有 `label_*` 字段只能在核实语义及维护方式后复用，不能把既有规则预测当作人工真值。
- 投稿标签按 `aid` 持久保存，搜索宽表只承载当前生效结果。当前 `adm_uniseek_videos` 按已确认数据日生成，限定 `is_deleted = false` 且累计收藏数严格大于100，并在发布时整批替换；不能仅在这张快照表上回填标签而不修改刷新逻辑。
- 现有搜索宽表未携带简介，推理阶段可离线读取源表；在线查询继续读取已发布搜索数据，避免引入实时LLM调用。
- 三个业务维度与任务状态分开：未处理、处理失败、拒答、解析失败、被前序判断跳过，都不能写成业务上的“否”。若为节省成本对非歌曲停止后续推理，明确记录后续维度未判定。
- 输出结构化标签与简短原文证据，并做格式及枚举校验。模型自报置信度不能直接视为经验证的准确率。
- 保存标注来源、模型版本、提示词／规范版本、输入摘要、标注时间与修正记录；人工修正优先，自动重跑不得无条件覆盖。
- 文本不足以判定歌声来源或语言时，保留不确定并进入复核队列；是否需要音频核验、覆盖多少投稿，由试跑结果决定。
- 支持断点续跑、按投稿及版本去重、有限重试与失败记录。首批回填后，只处理新增或相关文本变化的投稿；Daily播放、收藏等指标变化不应触发全文重判。
- 标签更新后同步发布新的搜索批次，使按 `batch_id` 识别更新的缓存失效，避免出现标签已更新、搜索结果仍旧的问题。

## 实施顺序

- [ ] 固定三维标注规范，补充歌曲MV、舞蹈BGM、真人翻唱、VUP、AI拟声、混合演唱、多语与资料缺失等正反例。
- [ ] 核实当前UniSeek规模、源字段完整度、现有 `label_*` 语义及上游维护关系，确定持久标签与搜索投影的存储方案。
- [ ] 建立人工样本集。建议先抽约1,000—2,000条起步，结合人工收录榜单（用户提到的“🀄️术50”）正例、UniSeek随机样本和各类易误收样本；未上榜不能直接视为负例。
- [ ] 分开用于调整提示词的样本与独立盲测样本；对相关作者、重复投稿或同曲版本造成的评测偏差作必要控制。
- [ ] 小规模试跑，分别评估是否歌曲、演唱来源、语言的质量，并直接抽查组合后的中V集合与日语虚拟歌曲集合。
- [ ] 记录误收、漏收、不确定率、各类覆盖情况、tokens、耗时、复核与重试成本，再确定模型和批量推理配置；不预先承诺20万条的准确率、费用或完成时间。
- [ ] 实现离线任务、持久标签、人工修正及版本管理，完成首批回填与增量维护。
- [ ] 将生效标签同步到ADM发布流程，验证刷新保留标签、失败保留旧批次、同日更新及缓存失效。
- [ ] 按确认的业务规则接入歌曲列表和UniSeek歌曲检索，确保关键词与AV/BV入口使用相同资格。
- [ ] 投稿标签稳定后，另行确定UP主聚合与默认展示规则，再实施创作者识别。

## 后续UP主识别与展示

用户提出的初始方向是：**在UniSeek收录集中有中V投稿，并且中V投稿率高于阈值的UP主，作为默认展示的创作者候选。** 该方向保留到第二阶段，当前不冻结阈值或具体计算公式。

实施账号打标前需明确：

- 分母是UniSeek收录投稿、本站已采集投稿，还是其他固定范围；收藏门槛筛过的集合不能直接称为账号完整历史投稿。
- 分子、分母、去重方式、统计时间范围、未判定投稿与低样本账号如何处理；不直接沿用语义尚未核实的 `videos_filtered`、`filter_pass_rate` 作为新口径。
- 比例与最低投稿数量的组合是否会漏掉新人或跨领域作者，以及是否提供人工修正与观察状态。
- 第一作者／上传者与 `staff` 参与作者采用什么统计关系；不能仅凭投稿标签推断完整创作职责。

账号规则确认并实现后，**创作者列表和UniSeek的创作者搜索结果默认只展示满足标记的账号**。歌曲结果按投稿自身标签判断，不因上传者未进入默认创作者集合而自动排除其合格歌曲。歌曲与账号两类资格应分别维护。

## 验收重点

- 舞蹈视频不会因使用中V歌曲BGM被误收；以歌曲为主体的MV可以通过。
- 真人、VUP本人演唱和AI拟声按政策排除；虚拟形象不直接决定歌声来源。
- 外语声库的中文演唱与中文声库的日语演唱，按实际演唱语言进入对应集合。
- 混合演唱、多语、无语言、资料缺失与任务失败均保留正确状态，不被强制归零或归否。
- 搬运不会导致合格歌曲在内容打标阶段被排除。
- 同一套投稿标签可支撑中V与未来日语业务，规则变动有版本记录，可复核、重算。
- 每日ADM刷新、标签单独更新与失败重试不会丢失标签、覆盖人工修正或提供半批结果。
- 投稿与账号筛选分别验收；本次记录方案不代表已完成生产数据打标或默认筛选上线。
