# ADM 日聚合：第一期建表与计算

状态：用户确认正式表、辅助表及核心脚本已创建，并完成单日执行；9:00自动调度待启用。更新：2026-10-26。

## 需求背景

现有视频逐日明细直接用于看板聚合查询较慢，需要按日预计算常用统计，降低接口实时扫描及关联成本。用户于2026-10-26确认正式表、辅助表和核心脚本已成功执行，随后一次聚合耗时约112.6秒并产生346行；目标日2026-10-20缺少21日期末快照，因此不代表数据完整。本次未连接数据库核验。

## 第一期范围

- 统一收录范围内的全量总计。
- 中术50固定样本集合总计，样本版本与名单对应。
- 旧分区：按 `type_id` 聚合。
- 新分区：按 `tid_v2` 聚合，不处理 `pid_v2`。

同一个数据范围使用统一收录集合。没有歌手标注的视频仍计入全量和分区。两套分区独立统计，不跨版本相加。

上述四类是明确白名单，不生成中术50×旧分区或中术50×新分区，也不做旧分区×新分区组合。

## 技术方案

采用一张日粒度宽表 `hantang_dynamic.adm_entity_metrics_daily`，通过数据范围、维度类型与对象键区分结果。七项指标（播放、收藏、点赞、硬币、分享、评论、弹幕）分别保存累计值和日增量。

明细 `record_date` 是北京时间凌晨约3±1小时的观测日期。D+1快照减D快照归入D日增长，同一行累计值取D+1快照。不把该观测区间描述为精确零点自然日。

具体表结构及字段语义统一维护在 [SQL表文档](../../sql/adm_entity_metrics_daily_draft.sql)，方案背景见[设计讨论草稿](../design/adm-daily-aggregation-draft.md)。本待办不代表所有候选口径已最终确认。

用户修改要求后，采用[PostgreSQL日聚合与存量回刷方案](../design/adm-postgresql-aggregation.md)：一天一个原子任务，计算四类结果后事务覆盖替换；失败重算当天，每次尝试均原子且有次数上限。历史回刷按日期拆分，允许不同日期先后完成，不要求整个日期范围原子切换。

只增加一张业务[任务辅助表](../../sql/adm_aggregation_task_draft.md)，保存日期、配置、状态、尝试次数和最近错误。第一期单worker，由pg_cron调用存储过程。此前分页、冻结输入及中间累计表方案废弃。对应[函数/过程](../../sql/adm_aggregation_routines.sql)和[安装脚本](../../sql/adm_aggregation_install.sql)已生成，通过15组隔离测试；辅助表和核心脚本已由用户创建，9:00调度尚未注册pg_cron。见[执行说明](../../sql/adm_aggregation_usage.md)。

## 卡点与待确认问题

- 已确认排除is_deleted=true，暂不依据is_filtered过滤；当前SQL将无投稿时间视为错误，新投稿缺期初不补零。需以真实数据验证这些保守策略。
- 缺失快照较常见，缺D快照影响D-1与D的增量；需明确完整性展示、回补和重算策略，不能缺失填0或将多日差分算作单日增长。已确认的[MySQL到PostgreSQL同步缺失](mysql-postgresql-sync-data-loss.md)由另一仓库owner修复并补数；本项目的查询与聚合结果验证须区分源数据缺失和计算失败。
- 采集边界附近的新投稿、旧视频补收录及元数据修改的历史归属需要确认。
- 核实 `(record_date, aid)` 唯一性、指标含义及中术50样本版本管理。
- 核实PostgreSQL版本、pg_cron安装配置能力及实际采集完成时间。
- 明确业务结果原子回滚而任务尝试/错误状态保留；严格缺失策略可能使全量指标经常为NULL，需要确认展示预期。
